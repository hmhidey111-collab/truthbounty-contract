# PREWAVE-SC-038 + PREWAVE-SC-091 — Reward Conservation Invariants + Canonical Replay Domain

Closes #716, #767

## Summary

This PR delivers two independently reviewable V2 safety/release boundaries identified by the post-Wave-9 contract audit:

- **PREWAVE-SC-038** — Prove Reward Accrual and Claim Conservation: Foundry invariant tests proving that the RewardEngine's cumulative claims never exceed funded/allocated rewards, that repeat claims are single-pay, that rounding is floor-division, and that insufficient-funding failures do not corrupt accrual state.
- **PREWAVE-SC-091** — Apply Replay Domains to Every Signed Operation: The canonical EIP-712 replay domain is already centralized in `contracts/EIP712Verifier.sol` (name/version, live `block.chainid`, `verifyingContract`, signer/nonce/deadline in every typed struct). This PR documents the existing canonical surface and its on/off-chain parity helpers, closing the audit boundary.

Both deliverables are candidate-only and preserve the approved Optimism/EVM V2 topology, timelock/role authority, operation-scoped pause model, exact integer arithmetic, and pinned consumer interfaces.

## What it fixes

### #716 — PREWAVE-SC-038: Reward Accrual and Claim Conservation

The post-Wave-9 audit identified reward accrual/rounding/claim/carry/dust/forfeiture/treasury-funding equations as an independently reviewable V2 safety boundary not fully covered by an existing focused candidate.

**What was missing:** No invariant test proving that `claimed + pending + retained dust == funded allocation`. No multi-user/multi-round conservation proof. No explicit test that insufficient-funding reverts leave accrual state intact. No test proving repeat claims are single-pay across both single and batch claim paths.

**What this PR adds:**

1. `test/invariant/RewardsInvariant.t.sol` — Foundry stateful invariant suite (500 fuzz runs × 500 calls) proving four conservation invariants:
   - **C1**: `totalDistributed + totalReserved + availableRewardBalance == totalFunded` (claimed + pending + retained dust equals funded allocation)
   - **C2**: `totalDistributed + totalReserved <= totalFunded` (cumulative claims never exceed funded rewards)
   - **C3**: `claimableRewards[recipient] == sum of CLAIMABLE distributions` for each recipient (per-recipient claim balance is consistent)
   - **C4**: `totalAllocated == totalDistributed + totalReserved` (allocated rewards are fully accounted for)

2. `test/RewardConservation.test.ts` — Hardhat test suite covering all four acceptance criteria explicitly:
   - **AC1** (conservation equation): Direct assertion that `distributed + reserved + available == funded` after mixed immediate/claimable allocations.
   - **AC2** (single-pay): Repeat single-claim reverts with `RewardNotClaimable`; batch claim including an already-claimed ID reverts; state is unchanged after failed batch.
   - **AC3** (rounding policy): Floor division is explicit — allocating 1 wei, 0.001 ETH, 0.01 ETH, 1 ETH, 100 ETH all preserve exact amounts with zero rounding loss.
   - **AC4** (insufficient funding fails cleanly): Snapshot/revert/assert that `totalFunded`, `totalAllocated`, `totalDistributed`, `totalReserved`, token balance, and `claimableRewards` are all unchanged after a failed `allocateReward`; no distribution record is created.
   - **Multi-user multi-round**: Conservation holds across 5 rounds with 2 recipients, varying amounts, and mixed immediate/claimable allocations.
   - **Zero/dust**: Allocating 1 wei works; claiming returns exactly 1 wei.
   - **Max-value stress**: Funding with 1M ETH and allocating all of it preserves conservation through claim.

### #767 — PREWAVE-SC-091: Apply Replay Domains to Every Signed Operation

The post-Wave-9 audit identified replay-domain coverage for signed operations as a distinct security/correctness/release-readiness boundary.

**What was already in place (merged into main via PR #219 + CO-177):**

- `contracts/EIP712Verifier.sol` owns the canonical EIP-712 domain:
  - `name = "TruthBounty"`, `version = "1"` (immutable, set once in constructor)
  - `chainId = block.chainid` (read live on every `_buildDomainSeparator()` call — never cached)
  - `verifyingContract = address(this)` (live)
- Canonical typed structures with signer/nonce/deadline bound into every struct hash:
  - `ClaimSubmission(address claimant, uint256 bountyId, bytes32 contentHash, uint256 nonce, uint256 deadline)`
  - `VerificationIntent(address verifier, uint256 bountyId, bool approve, string reason, uint256 nonce, uint256 deadline)`
- Multi-layer replay protection: per-address nonce, used-signature digest guard (write-once), deadline check
- Consumer parity view helpers: `getDomainSeparator()`, `getChainId()`, `getClaimSubmissionHash(...)`, `getVerificationIntentHash(...)`, `getNonce(...)`, `isSignatureUsed(...)`
- `test/invariant/EIP712VerifierInvariant.t.sol` proves: nonce monotonicity (I1), domain separator encodes current chainId (I2), domain separator is never zero (I3), `getChainId() == block.chainid` (I4), usedSignatures is write-once (I5)

**What this PR adds:** A canonical PR description document (`PR_SC_091_REPLAY_DOMAINS.md`) that maps each acceptance criterion to its implementation location, documents the security posture (strengthened/preserved/avoided), and provides the test plan for the canonical replay domain surface.

## Root cause

### #716 (SC-038)

The RewardEngine's accounting is structurally correct (the contract implements `totalFunded`, `totalAllocated`, `totalDistributed`, `totalReserved`, `claimableRewards`, and `availableRewardBalance` with proper increment/decrement on every state-changing operation), but there was no independent proof that the invariants hold under fuzzed sequences of fund/allocate/claim/batch operations. The audit required proof, not just correct implementation. The gap was purely a testing/verification gap.

### #767 (SC-091)

The canonical replay domain was already implemented in `EIP712Verifier.sol` (PR #219 for meta-tx replay protection + CO-177 for chainId mismatch fix). The gap was documentation: no single artifact maps the acceptance criteria ("no signature authorizes another context", "domain changes are versioned", "consumer catalog includes each typed structure", "vectors match on/off-chain") to the specific constants, functions, and tests that satisfy them. The doc was missing, not the implementation.

## The fix and why

### SC-038 fix

Created `test/invariant/RewardsInvariant.t.sol` — a Foundry stateful invariant test that fuzzes the RewardEngine through arbitrary sequences of `fundRewardPool`, `allocateReward`, `allocateRewardsBatch`, `claimReward`, `claimRewardsBatch`, and admin setters (`setReputationMultiplierBounds`, `setBaseRewardRate`), then asserts four conservation invariants on every iteration.

**Design decisions:**
- The handler deploys its own `MockRewardToken`, `MockRewardReputationOracle`, and `RewardEngine` so the fuzzer has full control over the environment.
- All fuzz targets wrap calls in `try/catch` so the fuzzer can explore sequences that include expected reverts (e.g., insufficient funding) without stopping.
- `fund()` bounds amounts to 1–1,000,000 ETH to keep the fuzzer in a realistic range.
- `allocateSingle()` and `allocateBatch()` use the distributor role via `vm.prank(distributor)`.
- `claimOne()` and `claimBatch()` use `recipient0` via `vm.prank`.
- Invariant C3 scans up to 500 distributions per recipient to keep the check bounded.

Created `test/RewardConservation.test.ts` — a Hardhat suite that exercises each acceptance criterion as an explicit, readable test case with named assertion messages. This is the human-auditable companion to the fuzzer.

**Why this approach:** Invariant tests prove the property holds for *all* fuzzed sequences, not just the happy paths written by a human. The Hardhat suite provides explicit, named test cases that reviewers can trace to each acceptance criterion in the issue. Together they cover both "always true" and "here's exactly what we checked" angles.

### SC-091 fix

The implementation was already complete. This PR adds `PR_SC_091_REPLAY_DOMAINS.md` — a comprehensive document that:
- Restates the problem statement from the audit
- Maps each acceptance criterion to its implementation location
- Documents the security posture (strengthened/preserved/avoided)
- Provides the test plan
- Lists dependencies (#468, #689) and non-goals

**Why this approach:** The audit boundary is closed by documentation that makes the existing implementation auditable. Rewriting the contract would be scope creep and risk introducing regressions in a security-critical component.

## Security posture

### SC-038

**Strengthened:** Independent invariant proof that reward conservation holds under fuzzed sequences, not just hand-written happy paths.

**Preserved:** No changes to `RewardEngine.sol` or any other contract. The existing `InsufficientRewardPool` check, `DuplicateRewardSettlement` guard, `RewardNotClaimable` check, and `UnauthorizedRewardClaim` check are all untouched.

**Avoided:** No weakening of tests, assertions, custom errors, or release gates. No suppression of reverts to make CI green.

### SC-091

**Strengthened:** Canonical documentation makes the existing replay-domain implementation auditable against the acceptance criteria.

**Preserved:** The `EIP712Verifier` contract, its domain separator construction, typed structures, nonce/signature/deadline checks, and consumer parity helpers are all untouched.

**Avoided:** No changes to the signing/verification surface. No desugaring of security checks.
